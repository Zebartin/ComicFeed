# ADR 0004: 下载并发模型——批次串行 + 手动单发受池约束

日期: 2026-08-03

## 背景

CONTEXT.md 曾承诺"全局 worker 池 + 每源独立队列 + 空闲 worker 自动取任务"的并发模型，但实际代码从未兑现：

- `download_batch`（订阅巡检、批量手动）对任务列表**顺序 `await`**，单个批次内完全串行，全局/每源信号量从不竞争
- 手动单画廊下载与失败重试通过 `asyncio.create_task` 并发运行，却**绕过 `DownloadPool`**，无任何并发上限
- 设置项 `global_concurrency`（UI 上的"并发数"）从未被读取，`main.py` 硬编码 `max_workers=5`
- `DownloadPool.set_source_limit()` 定义后从无调用点，每源槽位概念未接线

结果是：并发基础设施是死代码，而唯一真正并发的手动下载路径反而失控。

## 决策

1. **批次下载保持串行**：订阅巡检、批量手动下载按任务顺序执行，一次只下载一个画廊。这是对源站的礼貌策略，避免瞬时压力与 429。
2. **手动单画廊下载 / 失败重试走 `DownloadPool`**：通过 `pool.download()` 获取全局与每源信号量后再执行，使其受并发上限约束。
3. **并发数从设置读取**：`DownloadPool` 以 `global_concurrency` 设置构造（缺省 5），UI"并发数"生效。
4. **每源槽位（`set_source_limit`）暂不接线**：当前无 UI 暴露该配置，保留方法但不在本轮启用，待需要时为源配置增加槽位字段。

## 替代方案

### 方案 A: 真正实现批次内并发

`download_batch` 并发启动任务并受信号量约束。优点：兑现最初文档承诺、吞吐更高。缺点：对 exhentai 等风控严格的源站瞬时压力大，被封 IP 风险显著；当前批次串行在单用户单源场景下吞吐已够用。

### 方案 B: 删掉全部并发代码

接受串行为唯一行为，删除信号量、池、以及 UI"并发数"设置。优点：代码最少。缺点：手动多画廊同时下载时无任何限制，多个浏览器操作叠加可压垮源站；"并发数"设置已存在，用户会期待它生效。

## 理由

1. **礼貌优先于吞吐**：本系统的下载目标是长期、高频巡检多个订阅，源站限速（429）是主要风险。串行批次将单源瞬时请求量压到最低。
2. **封住真正的洞**：唯一无约束的并发路径（手动单发/重试）通过池纳入限制，改动小、风险低，即可消除"多请求叠加压垮源站"的风险。
3. **设置生效**：`global_concurrency` 已在 UI 和配置默认中存在，只是从未接线；读取它是低成本的正确性修复。
4. **每源槽位留待 UI 决策**：它是 CONTEXT 承诺的一部分，但接线需要新增源配置字段与表单，属于另一轮工作，不宜混入本轮。

## 后果

- `download_batch` 对同一批次的画廊仍顺序执行，批次间（多个巡检/手动请求并发）通过信号量限制全局并发
- 手动单画廊下载需经由 `get_download_pool()` 获取应用级池实例
- 相同画廊的并发下载（巡检批次 + 手动单发）在每源槽位 >1 时仍共用 `.cache/{gallery_id}` 目录存在竞态；每源槽位默认 1 时由信号量串行化，风险消除
- 后续如需提高吞吐，可逐步将批次内并发作为独立能力引入，而不影响手动路径的约束
