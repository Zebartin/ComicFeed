# ADR 0005: 通知摘要——事件驱动改为定时聚合

日期: 2026-08-05

## 背景

原通知机制是**事件驱动**：`download_batch` 每完成一个批次的下载就调用 `notify_batch` 发送邮件 + Webhook + 触发 Komga 扫描。由于订阅巡检逐订阅执行，实际表现为"每个订阅每更新一次就通知一次"。

问题：
- **通知风暴**：多个订阅在短时间内先后完成，用户收到多条零散通知
- **Komga 扫描耦合在通知里**：`_komga_scan` 位于 `notify_batch` 内部，通知发送失败会连带阻塞扫描；扫描时机无法独立控制
- **无法聚合**：没有任何地方留存"哪个订阅 → 下载了哪些画廊"，`subscription_gallery` 关联表早已随迁移删除，数据库无法回答"这间隔下了什么"

## 决策

将通知改为**定时摘要 (digest)** 模型：

1. **新增 `download_event` 持久化表**：`download_batch` 每完成/失败一个画廊插一行（含 subscription_id/name、gallery_id、标题、封面、web_url、页数、status、error、时间戳）。手动下载同样记录，`subscription_id` 为空、组名记为"手动下载"。
2. **Komga 扫描与通知解耦**：`_komga_scan` 移到 `download_batch` 末尾，下载完成即触发；通知只在定时 digest 时发生。
3. **单一全局 cron**：设置项 `notification_cron`（cron 表达式，空 = 不发送）。APScheduler 注册 cron job，设置变更时重排。`last_digest_at` 全局设置记录上次成功消费点。
4. **Digest 生成**：查询 `created_at > last_digest_at` 的事件；**无任何行则跳过**（不发、不推进时间戳）。按订阅分组：只列有下载/失败的订阅，每订阅成功结果限量（邮件 ≤12 / Webhook ≤5，超出省略），失败项（≤5）在组内列出。发送后**至少一个通道成功才推进** `last_digest_at`；全失败保持原值，下次重试。
5. **源错误通知保持即时**：源不可用/搜索失败是运维警报，仍走 Webhook 即时发送，不进 digest。

## 替代方案

### 方案 A: 保持事件驱动，仅去重合并

短时间窗内合并通知。缺点：仍需临时窗口/去重逻辑，且"每订阅一条"的根本形态没变，用户无法按自己的节奏收报告。

### 方案 B: 内存缓冲聚合

模块级 list 累积下载事件，cron 消费后清空。缺点：服务重启即丢失"已下载未通知"的内容，对按天级别的长间隔是真实风险（隔夜部署常见）。

### 方案 C: 每订阅独立通知时间

每个订阅可配自己的 cron。缺点：与"列出所有订阅项"的聚合诉求矛盾，复杂度高。

## 理由

1. **聚合优于即时**：用户收一条摘要而非多条零散通知，信息密度更高；跳过空间隔减少噪音。
2. **持久化优于内存**：长间隔下重启不丢，且为未来"历史下载记录"留底；SQLite 全量存储是项目既有形态。
3. **Komga 解耦**：库新鲜度是核心体验（下载内容由 Komga 索引），扫描必须尽快执行，不能等通知；与通知解耦后各自职责单一。
4. **源错误即时**：运维警报时效敏感，等 digest 会掩盖"订阅管道已断"的事实。

## 后果

- `notify_batch` 从 `download_batch` 移除；`download_batch` 增加每画廊一次 `download_event` 插入
- 通知设置页新增 cron 字段与说明；未配置 cron 时无任何 digest 通知
- `last_digest_at` 推进失败会致下次重复发送（罕见，日志可查）
- 手动单发下载从"完全静默"变为"进入 digest"（队列页仍即时可见）
